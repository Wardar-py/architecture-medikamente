# Анализ безопасности системы (As-Is)

## 1. Цель анализа

Проанализировать текущее состояние (As-Is) работы «Медикаменте» с данными,
выявить конфиденциальные данные, которые не учтены во внутренних системах,
описать потоки данных (DFD) и составить список проблемных зон с точки зрения
конфиденциальности, целостности и доступности данных (CIA).

Анализ выполнен с опорой на принципы **Privacy by Design**, **Data Minimization**
и **Data Lineage**, а также на требования законодательства РФ (152-ФЗ
«О персональных данных», приказы ФСТЭК/ФСБ по защите ПДн).

## 2. Выявленные конфиденциальные данные

| Категория                           | Примеры данных                                         | Где хранится сейчас                                      | Учтено в системах         |
|-------------------------------------|--------------------------------------------------------|----------------------------------------------------------|---------------------------|
| Идентификационные ПДн               | Ф. И. О., дата рождения                                | Excel `Patients`, журналы                                | Частично (Excel)          |
| Контактные ПДн                      | Телефон, e-mail                                        | Excel `Patients`, Outlook                                | Нет отдельного учёта      |
| Расширенные ПДн                     | Адрес прописки, место работы/учёбы                     | Сканы, PDF, Excel                                        | Нет                       |
| Специальная категория (медицинские) | Диагнозы, хронические заболевания, анализы, заключения | JPG/PDF/Excel в папках `Pacients`, `Laboratory Registry` | Нет (только файлы)        |
| Финансовые данные                   | Оплаты, чеки, договоры                                 | 1С:Бухгалтерия, ККМ, Excel кассиров                      | Частично (двойной учёт)   |
| Данные сотрудников (HR)             | Кадры, зарплаты, налоги                                | 1С:Бухгалтерия                                           | Частично                  |

**Ключевая проблема:** специальные категории ПДн (медицинские данные) и
расширенные ПДн вообще не учтены в информационных системах - они лежат
«рядом с пользователем» в файлах на общем диске без реестра, без владельца
и без контроля доступа.

## 3. Аудит мер по обеспечению безопасности (As-Is)

| Мера                                 | Требование                 | Состояние As-Is                                           |
|--------------------------------------|----------------------------|-----------------------------------------------------------|
| Учёт (реестр) ПДн и мест обработки   | 152-ФЗ, ст. 18.1           | Отсутствует                                               |
| Разграничение доступа (RBAC/ABAC)    | Мин. необходимый доступ    | Только доменная аутентификация AD, доступ к папкам «всем» |
| Шифрование at rest                   | Защита носителей           | Нет (файлы в открытом виде)                               |
| Шифрование in transit                | Защита каналов             | SMB/OLE/TCP без TLS                                       |
| Аудит и логирование доступа          | Отслеживание действий      | Нет аудита действий с файлами                             |
| Минимизация данных                   | Data Minimization          | Собираются избыточные данные, дубли                       |
| Резервное копирование / DR           | Доступность                | Один физический сервер в здании офиса (SPOF)              |
| Обезличивание для аналитики          | Privacy by Design          | Аналитика на «сырых» Excel с ПДн                          |
| Управление согласиями и удалением    | Право на забвение (152-ФЗ) | Нет механизма удаления/отзыва                             |
| Классификация/тегирование данных     | Data Governance            | Отсутствует                                               |

## 4. Список проблемных зон

### 4.1. Организационные и правовые
1. **Нет реестра ПДн и модели угроз** - компания не знает, какие ПДн, где и зачем обрабатываются (нарушение 152-ФЗ ст. 18.1).
2. **Нет разделения ответственности** за данные: отсутствуют владельцы доменов данных.
3. **Двойной ручной учёт платежей** (Excel + 1С) - риск расхождений и потери целостности.
4. **Нет процедуры реагирования на инциденты** утечки данных.
5. **Нет управления согласиями субъекта ПДн** и механизма реализации «права на забвение».

### 4.2. Хранение данных (at rest)
6. **Конфиденциальные данные в открытых файлах** (Excel/JPG/PDF) на общем файловом сервере - нет шифрования.
7. **Избыточность и дублирование** (папка на каждого пациента, множество журналов по врачам) - усложняет контроль и минимизацию.
8. **Единая точка отказа** - один физический сервер в офисе, нет резервирования и off-site backup.
9. **Нет тегирования/классификации** файлов - невозможно применить политики защиты.

### 4.3. Передача данных (in transit)
10. **Внутренние потоки данных не контролируются** - нет ограничений между системами, кроме бизнес-процессов.
11. **Незащищённые протоколы** - SMB (файловый доступ), OLE/TCP (ККМ<->1С) без шифрования.
12. **Отсутствие сегментации сети** - любой сотрудник в домене видит общий диск.

### 4.4. Доступ и контроль
13. **Отсутствует принцип минимальных привилегий** - доступ к папкам открыт широко, кассир видит медданные и наоборот.
14. **Нет аудита действий** - невозможно установить, кто и когда читал/менял данные.
15. **Нет защиты от «горизонтального» доступа** - сотрудник может открыть данные любого пациента.

### 4.5. Аналитика
16. **Аналитика (P&L, ABC) строится на «сырых» Excel с ПДн** - нет обезличивания, риск утечки при выгрузках.

## 5. Что можно улучшить (направления)

- Внедрить **реестр данных и каталог** с владельцами доменов (Data Governance).
- Перейти к **централизованному хранилищу** (PostgreSQL/S3) с шифрованием at rest и TLS in transit.
- Ввести **RBAC/ABAC** и принцип минимальных привилегий, разделить данные по доменам.
- Внедрить **тегирование данных** и DLP.
- Организовать **аудит доступа** (журналы, SIEM), мониторинг и алертинг аномалий.
- Для аналитики - **обезличивание/псевдонимизация** и отдельный аналитический слой (Data Lake) по Privacy by Design.
- Внедрить механизм **согласий и удаления** ПДн (право на забвение).

## 6. Список данных для защиты и способы защиты

| Данные                          | Уровень         | Шифрование           | Обфускация          | Обезличивание |
|---------------------------------|-----------------|----------------------|---------------------|---------------|
| Ф. И. О., дата рождения         | ПДн             | ✅ at rest/in transit | -                   | ✅ аналитика   |
| Телефон, e-mail                 | ПДн             | ✅                    | ✅ маскирование      | ✅             |
| Адрес, место работы/учёбы       | ПДн             | ✅                    | ✅                   | ✅             |
| Диагнозы, анализы, заключения   | Спец. категория | ✅ усиленное          | ✅                   | ✅ агрегация   |
| Договоры, платежи, чеки         | Финансовые      | ✅                    | ✅ маскирование карт | ✅             |
| Кадры, зарплаты                 | HR/финансовые   | ✅                    | ✅                   | ✅             |
| Учётные записи, токены доступа  | Секреты         | ✅ KMS или Vault      | -                   | -             |

Пояснение способов:
- **Шифрование** - данные нечитаемы без ключа (TDE/AES-256 at rest, TLS 1.2+ in transit, ключи в KMS/Vault). Применяется для хранения и передачи чувствительных данных.
- **Обфускация/маскирование** - сокрытие части данных в UI/логах (напр. `+7 *** ** 34`). Для отображения нижним ролям и в журналах.
- **Обезличивание/псевдонимизация** - удаление/замена идентификаторов для аналитики, ML/BI (Data Lake), чтобы работать с данными без риска идентификации субъекта.

## 7. Механизм тегирования данных

Предлагается модель тегирования на уровне метаданных с использованием
инструментов Data Governance/каталога данных.

**Схема тегов (пример):**

| Тег               | Значения                                              | Назначение                 |
|-------------------|-------------------------------------------------------|----------------------------|
| `data.class`      | `public` / `internal` / `confidential` / `sensitive`  | Класс конфиденциальности   |
| `data.category`   | `pii` / `medical` / `financial` / `hr` / `secret`     | Категория данных           |
| `data.subject`    | `patient` / `employee`                                | Субъект данных             |
| `data.retention`  | `1y` / `3y` / `till_consent_revoke`                   | Срок хранения / удаление   |
| `data.protection` | `encrypt` / `mask` / `anonymize`                      | Требуемая мера защиты      |
| `data.owner`      | `reception` / `clinic` / `finance` / `lab`            | Владелец домена            |

**Инструменты тегирования и управления метаданными:**
- **OpenMetadata / DataHub / Apache Atlas** - каталог данных, классификаторы, глоссарий, Data Lineage.
- Автоматические классификаторы (regex/NER/ML) для распознавания ПДн при загрузке.
- Политики на основе тегов (tag-based policies) в СУБД и Data Lake, интеграция с DLP и системой мониторинга.
- Теги используются CI-проверками релизов и системой аудита/алертинга.

## 8. Инструменты, способы и меры для обеспечения конфиденциальности потоков

| Этап потока           | Меры и инструменты                                                               |
|-----------------------|----------------------------------------------------------------------------------|
| Ввод/сбор данных      | Минимизация полей, согласие субъекта, валидация, тегирование при создании        |
| Хранение (at rest)    | Шифрование БД/дисков (TDE, AES-256), KMS/Vault, RBAC/ABAC, разделение по доменам |
| Передача (in transit) | TLS 1.2+/mTLS, API Gateway, сегментация сети, VPN                                |
| Доступ                | RBAC/ABAC, минимальные привилегии, MFA, запрет «горизонтального» доступа         |
| Аналитика             | Обезличивание/псевдонимизация, отдельный Data Lake, доступ по ролям              |
| Контроль              | Аудит доступа, DLP, SIEM, мониторинг и алертинг аномалий                         |
| Удаление              | Процедуры retention, защищённое удаление                                         |
