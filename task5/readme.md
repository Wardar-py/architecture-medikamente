# Разработка cutover-плана

## 1. Анализ ситуации и выбор стратегии

Мигрируем с монолитных/файловых систем на микросервисную архитектуру.
Особенности:
- Обрабатываются **медицинские данные и ПДн** - недопустимы простои и потеря данных.
- Бизнес работает непрерывно (приём пациентов, оплаты).
- Команда небольшая, опыта микросервисов мало.
- Первый шаг - **MVP** (самозапись пациента через портал + видимость на ресепшене).

### Сравнение вариантов

| Вариант               | Плюсы                                                                                   | Минусы                                                   | Применимость                         |
|-----------------------|-----------------------------------------------------------------------------------------|----------------------------------------------------------|--------------------------------------|
| High-level design     | Чистая архитектура, доменные границы                                                    | Не описывает сам процесс переключения; риск «big bang»   | Как основа, но не как cutover        |
| **Parallel run**      | Старая и новая системы работают вместе; безопасное сравнение; лёгкий откат; нет простоя | Дороже (двойная нагрузка); нужна синхронизация данных    | Оптимально для медицины              |
| Branch by abstraction | Плавный перенос слой за слоем; малые изменения                                          | Долго; сложность абстракций и совместимости версий       | Для внутренней декомпозиции монолита |

### Выбор: **Parallel run** + Branch by abstraction

**Обоснование:** для медицинской организации критичны непрерывность и целостность данных.
Parallel run позволяет запустить новую систему рядом со старой, сверять результаты и мгновенно откатиться без простоя. 
Branch by abstraction используется внутри как приём поэтапного переноса функциональности за абстракциями.

**Ограничения Parallel run:** необходима надёжная синхронизация данных между старой и новой системами и контроль расхождений.

## 3. План отката (rollback)

- На каждом этапе фиксируется **точка отката** (снапшот БД, версия конфигурации).
- Во время parallel run старая система остаётся рабочей - откат = переключение трафика обратно через feature flags/маршрутизацию API Gateway.
- После cutover старая система держится в **read-only** как fallback до этапа 8.
- Критерии отката (go/no-go): критические дефекты, расхождение данных > порога, недоступность > SLA, инцидент ИБ.

## 4. Риски и распределение ролей

| Риск (по стратегии Parallel run)             | Мера снижения                                                             | Ответственный       |
|----------------------------------------------|---------------------------------------------------------------------------|---------------------|
| Рассинхронизация данных старой/новой систем  | Единый источник истины, CDC, идемпотентность, ежедневная сверка, алерты   | DevOps + аналитик   |
| Двойная нагрузка на инфраструктуру           | Масштабирование, мониторинг ресурсов                                      | DevOps              |
| Утечка ПДн при миграции                      | Шифрование, обезличивание, ограничение доступа, аудит                     | ИБ / DPO            |
| Ошибки при cutover                           | Короткое freeze-окно, чек-лист, дежурная команда, план отката             | Тех. директор       |
| Сопротивление/ошибки персонала               | Обучение, инструкции, hypercare                                           | Бизнес-аналитик     |

### Роли
- **Тех. директор (архитектор)** - общая ответственность, go/no-go решения.
- **DevOps / сетевой админ** - инфраструктура, синхронизация, cutover, откат.
- **Разработчики** - сервисы, адаптеры, интеграции.
- **QA** - тестирование и критерии выхода.
- **ИБ** - безопасность, защита ПДн, аудит.
- **Бизнес-аналитик** - UAT, обучение, коммуникация с отделами.
- **Поддержка** - hypercare после запуска.

## 5. Вывод

Для «Медикаменте» выбрана стратегия **Parallel run** (с элементами branch by abstraction для декомпозиции), обеспечивающая непрерывность бизнеса, безопасный
откат и контроль целостности данных. Cutover-план разбит на 8 этапов с чёткими задачами, ответственными, сроками и мерами по снижению рисков.
